# T022 verified private ingestion and scoped routing

Qualified at source commit `daf2100629e87f672cdf371b95f42bb88f6bd2df`, tree `b48c03a3e3b430dd1d4e35178cf6026088b675a3`. Offline/synthetic only. No HTTP listener, Telegram poll/webhook registration, live membership/payment/supplier call, real credential/source row, deployment or normal runtime activation is introduced. Normal hosts still exit 78; BotHost --qualify-ingress is an explicit synthetic in-process native probe. The canonical 28-table SQL/catalog identity is unchanged.

TelegramWebhookVerifier binds one independently trusted registered BrandContext to a separate 32-byte random webhook secret. The adapter compares the digest of exactly one canonical secret header before parsing bounded JSON (1 MiB, depth 16); it rejects duplicate properties, caller brand/bot/deployment selectors, unsupported shapes/commands, malformed numbers, bot senders, groups/topics, mismatched sender/private-chat IDs, inline callbacks and callback messages authored by a different registered bot. A future HTTP adapter must require POST/application-json, preserve and reject repeated secret-header values, protect the secret/header with TLS/private routing and select the verifier from trusted bot deployment configuration. It must never take the verifier/context from request fields. This task qualifies the callable verifier, not an exposed transport endpoint or actual Telegram account identity. Webhook secrets are separate operator-provisioned protected input, not database encryption keys or .env/log/URL values. Dispose clears the owned digest; framework/caller-owned header/body strings cannot be guaranteed zeroed. Proof objects and errors have redacted representations and no public raw command/callback property.

UpdateRouter accepts only the opaque verified private proof. Supported navigation commands are /start, /menu, /support and /discounts. Product/order callbacks use a bounded canonical v1|revision|action|UUID format, actual sender membership, the saved message anchor and current flow revision. Foreign orders/listings, other actors, unknown memberships, stale anchors/revisions and expired continuations cannot mutate. /start alone may clear a previous bot-block marker after actual authenticated incoming private contact; bans remain enforced. Navigation opens a flow, never a payment, purchase, wallet credit/debit, stock allocation, support-ticket creation or credential release. Those handlers remain their own tasks. Protected future checkout operations must require the qualified channel proof; this router does not supply purchase authorization.

BotConsumerOwnership takes a transaction-scoped PostgreSQL advisory lock derived from the brand. Every routed write uses that same DbSession/transaction. Competing consumers for one bot return Busy without effects; another brand can proceed. Rollback/crash/connection loss releases ownership. This is serialized verified-webhook processing, not a long-poll daemon or durable polling offset; no polling consumer is activated. Any future polling adapter must separately qualify exclusive ownership before fetching and acknowledgement/offset recovery. Hash-key collisions can serialize unrelated work but cannot grant another brand's scope. Unknown commits retain the existing reconcile-before-retry policy; no remote callback is replayed by DbSession.

Nonfinancial navigation records a typed per-membership/update activity identity and suppresses a repeated command while that 180-day event exists. No raw message, callback, nonce, credential or provider payload is stored. Business replay protection does not depend on activity retention: callback revisions/anchors, unique active consent and domain idempotency remain authoritative. T087–T089 still own full activity taxonomy/retention/read APIs. A captured old command after event retention could repeat navigation only; it cannot authorize purchase or resurrect an old callback revision.

Private /bind adminUUID nonce messages pass the actual authenticated sender through the qualified two-channel binding primitive. They record no customer activity or membership and grant no backend session/staff authority until the independently authenticated admin completes the challenge. Wrong sender/nonce/expiry/epoch fails; nonce content never enters URL, diagnostics or ordinary activity/audit bodies.

Restock subscribe preflights membership/anchor/product/publication before invoking the trusted availability observer, releases that read transaction, then rechecks under owned business processing. RestockObservation is server-adapter evidence, never a request DTO: T032/T094 must supply real eligible out-of-stock observations, including paid-FIFO exclusion and current local/selected-source rules. Synthetic adapters provide those observations here. Product/listing revision, publication and a maximum 30-second observation age are checked again when consent is stored. No live provider behavior or complete catalog availability implementation is claimed. This observation controls consent only; actual first alert send must recheck current stock/publication/consent under T049/T051/T052 and may not promise stock or an availability date.

Consent reuses product_stock_subscriptions, unique active (membership,product); repeated callbacks cannot create a new stock cycle, while a fresh explicit post-cancellation callback creates a new consent ID. Unsubscribe works for the caller's waiting/known-unsent consent, including a hidden listing. It atomically cancels known unleased job/delivery work and closes consent without changing financial/order/coupon/stock state. Leased/uncertain/success-marked deliveries or leased/completed-send jobs block cancellation until reconciliation; never relabel unknown delivery as absent. Later send workers must serialize/revalidate the subscription/job/delivery before a possible network action. T051/T052 still qualify actual dispatch races/recovery. Closed rows keep their original timestamps; the 180-day cleanup is not run here.

Qualification uses generated secrets, synthetic private/group/forged envelopes and disposable PostgreSQL. Tests cover header/body bounds, duplicate fields, cross-bot messages, independent bot consumers, source proof, per-membership replay, stale/foreign targets before availability reads, consent/cancel/new cycle, stale observations, known-unsent cancellation, uncertain/leased preservation and actual bot-channel staff proof plus separate backend completion. Native BotHost parses/rejects real serialized synthetic envelopes; AotSmoke routes a verified private command through actual database ownership/flow/activity and suppresses its replay. Full business runtime, public transport hardening/rate limits, source/provider compatibility, private staff routing and operational release gates remain incomplete.
