# Local key and media verification
Run this on the existing AccAbad server. Keys and photos remain there. No media upload, archive extraction to disk, production database connection, bot stop, schema change, purchase, provider request or deployment is performed. The launcher installs its pinned Python dependencies into a separate user-state virtual environment, leaving the fleet's Python environment unchanged.

From the AccAbad fleet directory, after obtaining the latest `telegram-multi-bot-shop` main checkout on that server:
```bash
bash /path/to/telegram-multi-bot-shop/ops/verify-legacy-assets.sh --fleet-root "$PWD"
```
The script discovers available `instances/prod1/.env`, `instances/prod2/.env` and `instances/prod3/.env`. Their actual `INSTANCE_ENV_FILE` and `INSTANCE_DATA_DIR` bindings determine the application key file and media directory. Relative paths follow the fleet root, matching `fleet.sh`. It accepts literal dotenv quoting/comments/multiline values through the source's python-dotenv parser, never executes `.env` as shell code, never imports Django settings, never reads bot tokens into the keyring and never mixes ambient keys from another instance. Duplicate selected settings, unresolved variable interpolation, wrong instance identity or a non-production stage reject that instance; other instances continue.

The approved archive SHA-256 values and sizes are pinned in the verifier from the independent [backup assessment](PRODUCTION_BACKUP_RECONCILIATION.md). Default search locations are `.release/ci/backups` and `data/backups`; the script selects matching bytes, never a newer dump by filename or modification date. If those original archives are elsewhere, add their directory or individual paths:
```bash
bash /path/to/telegram-multi-bot-shop/ops/verify-legacy-assets.sh --fleet-root "$PWD" --backup-root /path/to/original/backups
```
`--backup-root` may be repeated; `--instance prod1` may restrict a run to one local instance. A host without kuala does not need its keys or media: unselected/unavailable instance directories are listed as `not_inspected`. Explicitly requested missing instances report a configuration exception. No whole media-directory traversal, copy or upload occurs. Archive discovery is limited to 10000 dump candidates; use a narrower backup location if necessary.

The verifier uses native `pg_restore` when available. Otherwise it runs only `pg_restore --data-only --file=-` through `docker compose ... exec -T postgres` in the existing fleet infrastructure container, streaming the archive on stdin. It never starts a container, mounts an archive into it, invokes a shell, supplies a database name or connects to PostgreSQL. The container must already be running. `--decoder native` or `--decoder docker` makes the choice explicit; `--pg-restore /path/to/pg_restore` selects a native binary. The decoder reads only the eight selected public tables. All temporary decrypted content remains in process memory; guaranteed erasure of immutable Python bytes/strings is not claimed.

## Checks and outputs
Current and previous Fernet keys follow pinned `AccAbad-Shop@66371a23a1c8149dc5bdf89a0355aa689d454dba/apps/common/crypto.py`: `FIELD_ENCRYPTION_KEY`, falling back only to the supplied `DJANGO_SECRET_KEY`, plus `FIELD_ENCRYPTION_KEY_PREVIOUS`; explicit Fernet keys and SHA-256-derived raw secrets are supported. There is no invented default key, TTL expiry on old tokens, plaintext fallback, remote credential lookup or output of key fingerprints, ciphertext, credentials or decrypted content. Selected fields are inventory data, submitted service JSON, supplier-connection credentials, supplier item content and supplier/preorder external-settlement references. Authentication and UTF-8/JSON validity are checked record-wise. Active/previous-key outcomes are counted; empty scopes report `not_exercised`, not a successful key qualification. This is source authentication, not target SC02 re-encryption/restore proof or a claim about every encrypted field in the source.

Each referenced local deposit proof is opened read-only beneath its configured media root. Relative media references and the original `/app/data/media/` container prefix are supported. Absolute unrelated paths, traversal, symlink descendants and special files are rejected. Saved byte counts and SHA-256 values are compared when present; a present file without a saved hash remains explicitly unverified. Missing acc-abad photos become individual exceptions without preventing remaining files, ciphertexts or other brands from being checked. Original source references remain untouched; a missing receipt is not grounds to discard its payment or infer a repayment. Product Telegram media references are counted as unverified without making Telegram calls.

The first launcher run may download public pinned packages; the verifier itself makes no network requests. Python 3.10 or newer with venv support and either native PostgreSQL client tools or the existing Docker fleet container are required. The command prints a new mode-0700 report directory outside both checkouts, normally under `~/.local/state/teleg-verification/`. Its two mode-0600 files are:
- `summary.json`: shareable aggregate results, archive hashes, the owner-confirmed brand labels, verification status and uninspected instances. **This is the only file to send back.**
- `exceptions.private.json`: local operator evidence identifying each affected source table/record/field and missing media reference. It contains no keys, ciphertext or decrypted content, but includes private record IDs and file paths. Keep it on the server; do not upload it, commit it or send it to CI.

Exit 0 means selected scoped checks found no exceptions; empty encrypted scopes still do not prove a key. Exit 1 means the report was written with per-record/per-instance exceptions or unverified product-media references. Exit 2 means setup/dependencies/output configuration prevented the run. The summary distinguishes configuration errors, absent pinned archives, decoder/archive rejection and record-inspection rejection. Every output retains `release_ready=false` and `target_reencryption_qualified=false`; T063/T064/T066/T068 remain open. No old key is retired.
