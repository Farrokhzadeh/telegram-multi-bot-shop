# Akunding read-only product inspection

This client implements documented read-only catalog listing and detail GETs. It returns account-specific single-unit price, stock and descriptive unit metadata in the supplier's USDT denomination. It does not bulk import or publish products, implement ISupplierAdapter, attest eligibility, bind a payable quote or expose any purchase operation. The administrator chooses individual credential/key/code products and exact mappings; unrelated catalog entries do not block a supplier integration.

Composition supplies an independently trusted HttpClient with same-account authorization from the existing protected credential snapshot, cookies disabled and automatic redirects disabled. Do not bind a default or untrusted transport to a normal host. Credential loading and host activation remain separate composition concerns. Authentication headers belong to that protected transport and are never returned by the client. Synthetic handler injection qualifies parsing only, not deployed credential custody or provider capability.

The product ID must match the requested identity. Required fields, exact decimal prices, consistent stock/availability, duplicate properties, HTTP failures, malformed payloads, bounded size and a 25-second linked deadline are checked. Caller cancellation propagates; other failures are sanitized and are never automatically retried. Stock zero remains descriptive sold-out metadata. Unit labels alone are not eligibility proof. Bulk-tier pricing is not used: this is a single-unit inspection, not a quantity purchase quotation.

Source: https://akunding.shop/api/docs (product detail and product-object sections). Tests contain generated public-shaped examples only, without supplier credentials, live-account catalog rows or account-specific observations. Full exact-commit CI supplies build, analyzer, formatting, test and native regression checks. T057/T091 procurement gates and FR-074 remain open. Before runtime composition, qualify the protected transport, current-account binding and exact product eligibility separately. No new dependency, table, migration or production operation is introduced.

## Protected administrator source preview

AkundingSourceInspection composes the client with SupplierCredentialSnapshot, matching the commerce deployment/service and exact configured account. It owns a nonredirecting, cookieless transport by default. An optional injected transport is a trusted qualification/composition dependency, never a caller-selected remote target. Each request resolves its bearer credential through the protected snapshot; the request header is cleared after transport. No token is returned in preview metadata or diagnostic text. Credential snapshot ownership stays with the caller.

InspectAsync requires a current independent administrator, an existing exact product/source mapping and its expected revision. Only Akunding mappings with canonical positive numeric external IDs and no variant qualify. It supports disabled candidate mappings for preview and performs no enable/select/publication mutation. It rechecks authentication and the product/source revision after the read, without retaining database locks over transport. Changed mappings, revocation and missing/disposed credentials reject the preview. The result preserves provider USDT metadata; it is not a CatalogStore ready-item observation or a purchase quote.

Generated credential files and disposable fixtures exercise authorization, account/deployment/service separation, changed-product and revoked-admin races, exact mapping and zero publication/procurement effects. No live-account results, actual keys or supplier product rows are saved. Normal hosts and the frozen administrator HTTP surface remain unchanged; an explicitly composed optional administrator extension can call this preview. Administrator-selected credential/key/code mappings remain the intended scope. Do not auto-import a catalog or infer readiness from a unit label. Purchasing, mapping enablement and runtime deployment retain their separate gates.

## Individual catalog selection

The protected internal administrator workflow now supports BrowseAsync and AddCandidateAsync. BrowseAsync reads the documented GET /api/v1/products?include_out_of_stock=true, validates the complete bounded response, searches locally by name or numeric ID and returns at most 100 entries ordered by ID with an exclusive after-ID continuation. Sold-out items remain selectable candidates. Each page is a fresh read, not a frozen catalog snapshot; changing supplier catalogs may change later pages. Responses above 1 MiB or 1,000 items, duplicate IDs and malformed metadata are rejected explicitly rather than silently truncated or converted to an empty catalog.

Both operations require the existing supplier shop product and its expected revision, current independent administrator authentication and the protected configured account. Authority and product revision are rechecked after transport, with no database locks held during the supplier call. AddCandidateAsync freshly verifies the chosen numeric product through the detail endpoint, then atomically writes only that exact disabled mapping through CreateAtRevisionAsync. The expected product revision is checked again under the product lock and bound into the audit commitment. Stable source/command IDs provide write replay; changed identity or expected revision cannot reuse a command. No bulk import occurs.

The returned product metadata is descriptive, not a ready-item attestation or binding price quote. An administrator may choose only their desired accounts, keys or codes; other supplier offerings do not imply publication or purchase. Existing eligibility, enablement, active-source selection, brand publication, complete-delivery and enforceable purchase-ceiling requirements still apply separately. These typed backend operations are exposed by the separately composed [optional supplier catalog HTTP extension](SUPPLIER_CATALOG_HTTP.md). They are not mounted by the normal hosts and do not add a dashboard or change the frozen administrator HTTP contract. Runtime connection and purchasing remain unfinished; T057/T091 remain open.

Qualification uses generated catalog rows and disposable database fixtures: search and continuation, sold-out choices, malformed/duplicate/overlarge catalogs, cancellation, rejected queries, revoked authority before/during transport, concurrent product changes, mismatched details, atomic stale-revision rejection and audited mapping replay. No actual catalog rows, supplier keys or account-specific results are saved. Full exact-commit CI is required before reporting this checkpoint as qualified.
