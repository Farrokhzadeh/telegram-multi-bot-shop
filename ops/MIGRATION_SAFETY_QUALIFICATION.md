## Manifest, target and provenance

VerifiedImportManifest freezes input bytes before checking a separately pinned digest, bounds every field/count/body and accepts only the canonical binary encoding without trailing data, unknown projections or duplicate source keys. It binds one source brand, source revision/schema digest, protected immutable snapshot reference/digest, batch, target brand and exact disposable SchemaManifest destination. These are synthetic evidence inputs, not proof of an actual deployed source schema. Production immutable archive custody/durability and the trust channel for real pinned manifests remain unqualified.

Destination writes require the actual connection endpoint/database/username, current database user, pinned server/baseline version and explicit legacy-import role. BrandContext must match the original target brand/bot. No production/staging destination is enabled. LegacyMapStore checks complete manifest membership, target kind/ID/brand, exact fingerprint, original batch and original protected manifest reference. Logical source identities serialize before lookup/insert; changed rows/targets/source scope/batches conflict. Existing immutable mapping and deferred finite target/ownership guards remain authoritative. Target and mapping writes commit together; disposal rolls back an incomplete transaction. No checkpoint, settings/EAV or extra import table is added.

Projection names are finite, documented provenance namespaces: users for the source primary identity; users.balance.snapshot for its frozen authoritative balance projected to the target wallet; users.balance.opening for the derived nonzero opening entry; transactions for actual source ledger primary IDs; and orders with distinct primary/public_order_reference key kinds. The two derived users.balance namespaces are explicitly field projections, not claims of additional physical source tables. Original source IDs and real aliases remain unmodified. Actual deployed source column/migration compatibility and the complete source-to-target inventory still require T063/E3.

## Financial projection and resume

OpeningBalanceImportWorkflow is deliberately limited to approved synthetic membership/wallet/history projections. It validates exact USD denomination, zero other-currency liabilities, nonnegative authoritative opening, representable original UTC timestamps and unique source/target identities before target writes. Non-USD, negative, zero-value historical movements or otherwise unrepresentable facts stop the affected projection; they are not coerced, discarded or converted to fictitious USD. Actual missing/unrepresentable history must remain in protected source evidence for review.

A positive opening creates one immutable posting with its original membership and exact USD amount, matching wallet version/balance, import-role provenance and manifest. A zero opening freezes a mapping and zero/version-zero wallet without fabricating a forbidden zero-value posting. Historical signed entries remain non-posting evidence, with no posting_version; they never add to the opening. Available history may be incomplete and sum to a different amount than the authoritative snapshot. Replay creates no new user, opening, ledger movement or audit and never resets the current wallet. Missing non-posting history can resume against the same full pinned manifest without reposting the opening. A changed frozen snapshot or reused ID with a different target/fingerprint conflicts. Same legacy/Telegram IDs in different source/target brands retain distinct memberships and wallets.

The reconciliation implementation is a bounded-scope preparation for T066. It reports pinned manifest/mapping completeness and mismatches, expected/frozen/current USD totals and differences, opening/non-posting counts, observed paid-unfulfilled/held/ciphertext counts and saleable inventory. Its explicit scope is qualified_wallet_projection_only and releaseReady is always false. It does not claim full historical snapshot, liability, coupon/source-payment, media or source-schema reconciliation. T066 remains unchecked. Reports exclude customer/source primary identifiers, credentials, ciphertext, key material and protected archive contents; diagnostic string forms are redacted. The exported CI artifact contains only synthetic aggregate evidence.

## Re-encryption and old-key retention

ReencryptionWorkflow reuses the T013 LegacyFernetReader and its existing Python-generated public golden vectors, including previous-source-key recovery. It neither replaces the source cipher nor weakens its authentication/plaintext-fallback rules. Approved brand fields use the actual brand/row/field SC02 context and current brand key; unsold shared credential bytes use the separately granted inventory key/scope. Bot-token rows must match the original brand. Every record encrypts, decrypts and compares bytes before returning ciphertext/key metadata. Temporary byte buffers are cleared and object string forms redact protected data; the existing legacy string reader necessarily uses managed strings, so guaranteed erasure of immutable strings is not claimed. No plaintext file/export is produced. Actual source/key ownership and deployed field representation remain T063/E3 evidence gates.

KeyRetirementGate verifies a pinned, bounded protected dependency manifest using strict source-generated JSON. Unknown/duplicate/missing/null fields and invalid references/digests/UTC horizons are rejected. Candidate review is blocked by incomplete inventory attestation, unbounded/equality/future retention, rollback/history dependency or missing restore/re-encryption verification. Eligibility means separate review only: mayDelete is always false and no deletion API exists. No actual old key, backup or private dependency inventory was opened, modified or retired. KEY_RETIREMENT_RUNBOOK.md retains real completeness/authenticity/restore and owner-decision gates. BRAND_CUTOVER_RUNBOOK.md requires one brand, verified writer/callback fences, protected frozen snapshots, reconciliation, no dual stock owner and an explicit rollback/release decision; it does not execute those steps.
