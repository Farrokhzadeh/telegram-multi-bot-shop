## Contract and source evidence

The signature contract was checked against the official NOWPayments help/API documentation and the provider-owned SDK: [IPN setup](https://nowpayments.zendesk.com/hc/en-us/articles/21395546303389-IPN-and-how-to-setup), [API documentation](https://documenter.getpostman.com/view/7907941/S1a32n38), and [pinned SDK IPN source](https://github.com/NowPaymentsIO/nowpayments-sdk-nodejs/blob/08e14f901804a08914ff88f4f1da7f1820bf2e08/src/ipn.js), blob 65a65fb9fa774a4d9349b1c5a42115345f56057d. No SDK was installed and no merchant account or provider endpoint was called. A local Node crypto/JSON implementation generated the independent public-key golden vector; the verifier is independently implemented in C#.

NowPaymentsIpnVerifier requires one well-formed signature header, bounded UTF-8 JSON and a protected configured IPN key. It computes HMAC-SHA512 over provider-compatible deep key sorting/stringification and compares bytes in constant time. Arrays retain order; integer property enumeration, Unicode, escapes and control characters are covered. Duplicate/escaped-duplicate names, prototype-sensitive keys, excessive depth/size and numbers outside the exact supported decimal domain fail closed. Financial arithmetic never passes through binary floating point. Numeric/string amount input is exact; safe-integer limits apply to numeric provider IDs. Unsupported payloads do not obtain a verified proof or a financial mutation.

The sealed disposable VerifiedPaymentNotice has no public constructor and redacts string output. Its private raw body is available only to trusted persistence for encryption and is cleared on disposal. Customer selectors do not determine membership/brand routing. A valid signature alone is insufficient: policy also matches the original provider ID, opaque local origin, USD quote, selected USDTTRC20/USDTBSC network and saved expected token amount. Only an exact full-value finished notice becomes ready for settlement verification. Under/excess, wrong-network/value and unknown states stay reviewed. Intermediate confirmed/sending states are not treated as finished settlement.

## Persistence and authorization

PaymentEvidenceStore creates standalone crypto-only topup intents with exclusive topup_user_id and no fake order or required wallet row. It enforces current brand crypto/topup/zero-balance initiation policy and original membership identity. Replay preserves the original amount/network; a changed/foreign replay rejects. Initiation eligibility is not reused as an eventual settlement-credit gate.

BindInvoiceAsync is a trusted service writer for an authenticated invoice response, not a customer DTO endpoint or a provider client. It saves provider identity and the positive expected network amount atomically and cannot rebind them. Invoice creation/uncertainty, authenticated provider lookup and runtime HTTP binding remain T039 work. Unsolicited callbacks cannot select or create an invoice binding.

CaptureAsync accepts only opaque verified notices matching an existing crypto/USD invoice in its server-resolved context. It encrypts raw evidence under the original payment's brand/row/field scope and supplies its digest, encryption key ID and ciphertext to an injected immutable archive port outside transactions. Archive failure leaves payment state untouched. Production archive durability/lookup and actual provider compatibility remain deployment/adapter gates; fixtures use an immutable in-memory archive shared across reconstructed stores, not a real object-storage service.

After archive acceptance, the writer serializes membership/order/payment state and saves typed scalar observations: actual token amount, recognized USD quote amount only for qualifying full evidence, optional real confirmation count, HMAC key ID/signature, canonical payload SHA-256, server verification time, protected evidence reference and raw digest. It captures database observation time before archive work, never accepts provider timestamps as the deadline authority, preserves the first recorded positive qualifying clock and does not revive expired/replaced orders. A timely live observation moves an awaiting order to confirmation_pending, preserving the original deadline. Delayed final confirmation and reordered intermediate notices retain that evidence. Zero-value waiting notices remain replaceable; anomalous money remains reviewed. Known confirmed evidence cannot be downgraded by an older intermediate notice.

Canonical replay identity suppresses duplicate verification jobs. A distinct event gets its own durable VerifyPayment work, so finishing after earlier pending work cannot lose a wakeup. One hundred concurrent requests, across reconstructed stores and an explicitly bounded 16-connection pool, produce one logical verification event. Existing settled history is preserved: a later distinct notice is archived/audited and queued once for reconciliation without rewriting the original accepted proof or posting money. Its audit retains the raw archive digest while logical dedupe uses the authenticated canonical event identity.

The canonical 28-table fresh disposable baseline adds positive expected_network_amount plus an all-or-none IPN key/signature/payload-hash/verified-time tuple. Actual tokens remain separate from the immutable expected token quote and USD quote. Existing order_id XOR topup_user_id, bank destination, network, provider identity, original quote and monetary history guards remain authoritative. There is no JSON column, duplicate payments table, invented target-kind enum or extra relation. Current SQL SHA-256: 8542537a0f8e15485e33a10e85dc73ecb621d5a6b040adeac393510c29a2dad0.
