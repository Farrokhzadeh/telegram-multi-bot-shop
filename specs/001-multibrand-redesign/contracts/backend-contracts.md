# Backend Contracts — v0 (No UI)

This is the API/event **contract inventory** for planning. Exact OpenAPI schemas, request validators and auth design are generated/locked during implementation, after provider inventory. Nothing here authorizes live traffic.

## Common rules

- Admin paths start `/v1/admin`; internal service paths `/v1/internal`; bot webhooks, if selected, use a separately authenticated transport endpoint.
- Administrator authenticates via a private, auditable API credential/session mechanism. Every mutating request validates role, object scope and idempotency key where money or delivery is involved.
- Bot/customer actions obtain brand context from the authenticated bot deployment identity or verified webhook secret, **never solely a customer-supplied brand ID**.
- Admin may select brand explicitly; audit events include admin actor, brand, target, request ID and redacted result.
- Standard errors: `validation_failed`, `quantity_exceeds_discount_limit` (with maximum allowed quantity), `order_payment_expired`, `not_found`, `forbidden`, `conflict`, `insufficient_funds`, `out_of_stock`, `payment_unconfirmed`, `provider_outcome_unknown`, `temporarily_unavailable`; no stack traces, secrets or foreign-brand identifiers.
- Monetary requests declare currency and exact decimal representation; every successful payment/checkout response includes immutable order/reference and committed status. Never infer paid status from a client redirect.
- Endpoints returning encrypted token values return metadata and last-updated/verification state, **never plaintext or ciphertext token fields**.

## Owner-approved supplier attempt contract (2026-10-29; design only)

- `supplier_requests` identifies a supplier **batch** for one order (`order_id`, positive `requested_quantity`), with one stable local `(provider_code,idempotency_key)` logical purchase, plus immutable original account/product/variant identity. Local key uniqueness does not prove remote idempotency. Never submit another purchase on `unknown` or `partial_pending_admin` solely because a worker reruns.
- `supplier_request_attempts` records durable intent **before** each possible remote `submit`, `status_lookup` or `export` call, `(supplier_request_id,attempt_no)` unique, with `in_flight`/terminal outcome and sanitized result/evidence refs. A crash after intent but before a provable response leaves `unknown`, never permission to blindly re-submit purchase. A `jobs` lease/retry is not itself an API attempt. Completed attempt evidence is immutable, no raw credentials/payload bodies/JSON.
- `fulfillments` retains per-unit identity and same-order supplier links, encryption and remote-item dedupe. For five requested/three acquired, retain the three internally with zero customer release and keep the whole paid order under review. Prepare/release one complete five-unit manifest only after all units are verified and review is cleared; do not automatically buy again, credit or record external refunds. Per-unit acquisition never bypasses whole-order access guards.
- Before executable DDL, validate provider idempotency and replayed batch item identity, actual historical source attempt cardinality, whole-order coupon redemption, complete-manifest access/transport guards and actual historical partial-order compatibility. No new external public supplier endpoint is implied by this history table.

## Ready-to-deliver supplier scope (owner approval 2026-10-30)

Mapping publication and pre-purchase validation accept only exact provider products/variants supplying ready accounts, keys or codes without buyer fulfillment inputs. No input-collecting activation, email-required slot, existing-account upgrade or manual/custom supplier flow. Unknown requirements are ineligible; new checkout must not charge/create an invoice for them.

If requirements change after accepted payment, keep the original source and paid/unfulfilled administrator-review state under FR-066, with no fallback purchase or automatic compensation. Status/lookup/export remains valid for asynchronous supplier processing; full-manifest release still gates delivery. Normal customer redemption of an already delivered key/code is allowed. No new input-form, activation API or table is introduced. FR-068 / SC-037; independently approved local/manual scope is unchanged.

## Optional local-preorder estimate contract (owner approval 2026-10-30)

A local-preorder product may have `expected_availability_date = NULL`; publication/checkout cannot require a date. Authorized product edits may set/update/clear an estimate. Quotes/orders preserve their original displayed estimate or absence, while current customer views distinguish no estimate from an estimated date. No guaranteed delivery deadline is invented.

Missing/passed/edited/cleared estimates cannot expire/cancel/reorder a paid obligation, release coupon uses or trigger compensation. Full-stock FIFO and independent unpaid payment deadlines still govern. Automatic date-change notifications and explicit admin paid-cancellation outcome/hold policy remain separate from the date field; cancellation requests use existing support under FR-070. FR-069 / SC-038; no new relation or endpoint is implied.

## Paid-preorder cancellation via existing support (owner approval 2026-10-30)

Use the existing support ticket/message surface with a checked same-member/brand `order_id`; no new cancellation-request route/button/table. Staff manually review/respond. Creating, assigning, replying to, closing or reopening support never changes order payment/fulfillment, FIFO, coupon, wallet or stock state.

A separate existing authorized admin order-resolution action, under reviewed outcome rules, records actor/reason and serializes with allocation; keep original payments/history and prevent stale post-resolution allocation. Support text/status is not a cancellation command or external settlement evidence. Final paid-cancellation outcome/hold and coupon/internal-wallet rules remain under review; no outside payout reference/record or automatic compensation is added. FR-070 / SC-039.

## Pricing and coupon policy freeze

- Each `brand_products` row has `price_usdt`, `price_toman`, `auto_price_toman`. Accepted `orders` retain `user_id`, `unit_price_usdt`, nullable `unit_price_toman`, `exchange_rate_toman`/fetched-at/source, `currency`, `payment_method`, `quantity`, immutable discount fields, rounding step and calculation version; **no order total columns** (`total_usdt`/`total_toman`), pricing-mode enum, `payable_usd`, `brand_id` or `telegram_id`. `payments.amount_due`, `payments.amount_received`, payment currency and the wallet ledger prove exact requested/settled money separately from reproducible derived quote totals.
- Pricing reproduces `main` source: Nobitex USDT/RLS divided by ten, hourly refresh, source staleness checks, upward-to-5,000-toman rounding **after** calculating discounted USDT total. Only current rate state lives on `brands`, accepted rate on each order.
- Coupon selection remains automatic/mandatory and applies across USDT/toman. **For 10%, 50% and 100% codes alike**, a code with 10 remaining **unheld** eligible uses **limits the allowed quantity to 10**: an attempted quantity 11 returns correction guidance and **does not create an order**, partially discount units or skip the code. For external bank/crypto payment, use a **temporary `discount_uses(status='held')`** quota claim at successful order creation without stock reservation; count both held and redeemed units against caps. Unpaid expiry or atomic replacement cancellation changes the hold to `released`. Timely bank receipt or qualified crypto evidence keeps the hold during review/confirmation, and paid bank orders pending restock keep it **until an explicit authorized admin action or fulfillment**; the bot cannot observe an off-bot refund. Fully fulfilled orders redeem exactly once; immediate non-preorder instant/free orders redeem atomically with allocation. New target preorders hold the whole claim while waiting and redeem it once at complete allocation/fulfillment; no split usage. Invalid quantity/failed/no-stock checkout consumes zero permanent uses.
- **Owner-approved prepaid issuance is one reusable code for `N` future units**, with `max_total_uses=N` and matching paid order; do not generate `N` coupon rows. **Prepaid codes are owner-approved account-bound**: each new prepaid discount requires `eligible_user_id` for the original paying member, a matching brand/source paid order, and checked product/units; knowing a code never authorizes a different customer or brand. Public promotions and goodwill retain separately controlled scope. The external bank/crypto temporary hold-and-release lifecycle is approved, **including returning coupons after verified crypto payment without stock in the same transaction as USD wallet compensation**. **Owner option A on expiration**: restore usage but keep original `ends_at`; an expired marketing code stays ineligible for new orders, no auto-replacement or renewal. A previously established valid held discount remains enforceable on its **original** protected order after promotion expiry. Prepaid future-unit entitlements default to `ends_at IS NULL` while paid liability remains outstanding; notify an unsuccessful purchaser clearly if their returned *marketing* use is expired. A fixed toman listing may still accept **USD wallet** or independently priced USDT crypto payment when `price_usdt` is positive; quote currency never changes merely because `auto_price_toman` is off. Wallet balances and ledger credits use **USD**, not USDT; the frozen USDT quote maps 1:1 numerically for shortage credit by explicit business policy.
- The current bot's “My Discounts” flow requires optional authorized reveal of a user's assigned code. Preserve code ciphertext encrypted under that brand's key plus a keyed digest for fast uniqueness/lookup; customers cannot reveal coupons assigned to another Telegram ID or brand.

## Approved compact wallet and Telegram customer transport

- Customer wallets are **USD-only**. `wallets` is keyed by `user_id` and `wallet_entries.user_id` references it; neither table carries `currency`. `orders.currency` and `payments.currency` still identify how the customer pays (USDT/toman) and must **not** be removed as a consequence.
- Customer conversations and marketing/order/support delivery are **private DMs only**. On an authenticated bot update, derive membership from `(brand_id,telegram_id)`; on outbound send/edit, derive chat ID from `users.telegram_id` through `telegram_deliveries.user_id`. No `telegram_deliveries.chat_id` or `telegram_sessions` table in v1.
- Required Telegram channels are external chat identities for join checks, **not** customer conversation destinations. Keep `brand_channels.chat_id` and the per-brand bot identity intact.
- Private DM behavior allows one revision-guarded `users.flow_*` cursor per brand membership. Concurrent stale callbacks must fail revision checks, and additional group/topic support requires a future schema change.

## Thirty-minute unpaid-payment window

- Bank/crypto checkout creates `orders.payment_due_at=created_at+30 minutes`, and the payment instruction prominently warns "Valid for 30 minutes only" plus the deadline in the store language.
- Payment status transitions `awaiting_payment → expired` only when deadline has passed **and no qualifying before-deadline payment evidence exists**. Submit receipt in time → `under_review`; qualifying crypto evidence observed in time → `confirmation_pending`. Neither can be timed out merely because the admin/provider takes longer than 30 minutes.
- Enqueue a durable edit intent using the Telegram ID retrieved via `orders.user_id → users.telegram_id`, the correct bot via `users.brand_id`, and the original payment message ID from `telegram_deliveries`. Edit the existing message to expired/failed; on Telegram error retry or explain on next interaction.
- Real funds observed/settled **after** expiry stay in immutable `payments` evidence; full-value verified USDT payments credit the original membership's **USD wallet exactly once** for the frozen quote without reviving/rebinding the old order or changing the released coupon. Staff reconcile partial/excess/wrong-network/uncertain crypto and all late bank transfers. Preserve source payment and wallet-entry linkage with explicit customer notification.

## Immutable payment method per order (confirmed)

- `orders.payment_method` and `orders.currency` are frozen at creation; **no switch-payment-method operation** exists. A customer changing from bank to crypto/wallet creates a **new order**. A previous same-membership **no-evidence `awaiting_payment`** order is automatically **cancelled when the new order successfully commits**, instead of waiting for its 30-minute expiry; if replacement fails validation, the original timer is unchanged. A partial unique index permits at most one `awaiting_payment` order per `user_id`; approved review/pending confirmation/paid orders are never cancelled automatically.
- Payment, receipt and provider reference identities are never transferred across the two orders. Late settlement against the original order remains an auditable reconciliation/compensation obligation.
- **Schema review gate (origin resolved)**: Current Django `main` creates `wallet_topup` attempts without product orders (see `apps/payments/models.py` and `apps/payments/services.py`). The new exclusive `order_id`/`topup_user_id` origin preserves them without fake product orders. Removing `payments.kind` or `payments.currency` remains **conditional on verifying historical quote/provider denominations**, not on inventing another table.

## Approved wallet-funding and external checkout routes

- **Wallet top-up**: NOWPayments crypto **only**, USD-valued frozen quote, no linked product order, one brand-membership origin `payments.topup_user_id → users.id`. No card-to-card funding or TOMAN wallet exists. Preserve existing topup gating, including the zero-balance restriction, pending separate policy review.
- **Product order**: `orders.payment_method='bank'` means card-to-card **TOMAN** settlement; `'crypto'` means NOWPayments external settlement against the product's USDT-derived **USD-valued** quote; `'wallet'` spends existing USD store credit atomically and does not generate an external invoice. Availability is still brand/listing scoped.
- **Separate receiving bank cards**: Each Iranian brand has its **own distinct active card**, stored in typed brand-encrypted `brands` fields rather than a new table. On TOMAN bank checkout, copy the card number/holder into immutable encrypted `payments` destination-snapshot fields, and display only the destination frozen for that payment. Card rotation must not change pending orders or receipt review. Reject accidental same-card reuse across the two active brands using a keyed digest, and redact details from logs. Banks may display common account-holder names despite distinct card numbers; check before public rollout.
- **Payments table**: exactly one of nullable `payments.order_id` or nullable `payments.topup_user_id` must be present, database-enforced. Top-up payment rows do not require a `wallets` row at creation, but verified settlement must create/update one with a single ledger posting. `kind/currency` are not removed before proving legacy/provider semantics; `network_asset`, `network_amount`, actual received quantity and provider evidence cannot be inferred from the USD display label.
- **NOWPayments invoice vs coin**: provider `price_currency='usd'` differs from crypto `pay_currency`. **Allowed pay currencies: `USDTTRC20` (TRON/TRC20) and `USDTBSC` (BNB Smart Chain/BEP20) only.** Do not accept native `TRX`/`BNB`, a generic networkless `USDT`, or any other assets. Compare the callback pay-currency against the exact network-specific selected invoice code and verify live availability. Confirm IPN verification and standalone top-up invoice expiry separately; order checkout retains its own 30-minute payment deadline. Do not treat a browser redirect or unverified webhook as money received.
- **Shared merchant account**: all three brands use one NOWPayments account and its centrally mounted platform credential/IPN secret, never a copy in each brand record. Allocate a globally unique internal invoice/reference, associate it with a stored `payments.id`, and attach brand-specific safe descriptions only as presentation.
