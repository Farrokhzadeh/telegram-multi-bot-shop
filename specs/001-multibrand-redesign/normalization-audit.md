## The rule for removing a column

A column is genuinely redundant only if there is **exactly one authoritative path** to recover it for **all valid lifecycle states**, including pending/unmapped history. Some apparently repeated fields are necessary snapshots (historic product name, original FX rate, frozen amounts) or concurrency controls (`discounts.redeemed_count`). Removing brand IDs often trades one scalar column for database triggers and extra joins; it is not automatically safer or cheaper.

Labels below:

- **REMOVE**: Preferred logical simplification, subject to normal migration and test signoff.
- **CONDITIONAL**: Remove only if the stated business restriction is confirmed.
- **KEEP**: Repetition is intentional for correctness, history, or performance.

### Approved relation audit: tables 24–27

- **24. `discount_revisions` — KEEP.** Immutable typed snapshots per coupon issuance/owner edit, unique `(discount_id,revision_no)`, tied to exactly one `audit_events` actor/time/reason record. `discounts.revision` advances under the coupon lock in the same transaction. Capture owner-editable terms and the real redeemed/held counters at the edit instant; customer redemptions do not create owner-edit revisions. This fulfills FR-058 without generic EAV, JSON or nullable coupon-specific columns on every ordinary audit event.
- **25. `bot_activity_events` — KEEP.** Brand-membership-scoped, append-only record of meaningful bot start, navigation, product views, whitelisted button actions, quantity/checkout progression, actual abandonment/timeout and relevant errors. Optional typed product/order/support references require database brand guards; source Telegram update and flow revision are evidence, not authorization. Unique per-user deterministic idempotency for update/worker retries. Do not store raw Telegram messages or callback payloads, payment secrets or arbitrary metadata. Finalize the finite event registry and technical cleanup/privacy design for the owner-approved 180-day nonfinancial retention under FR-071; `users.flow_*` and `telegram_deliveries` are not substitutes for interaction history.
- **26. `supplier_request_attempts` — KEEP (owner-approved 2026-10-29).** Before each potentially remote supplier submit/lookup/export, persist a typed attempt intent that is finalized as known or `unknown` with `supplier_request_id`, monotonic `attempt_no`, operation, outcome, optional sanitized HTTP/remote/error/evidence refs, timestamps and `(supplier_request_id,attempt_no)` uniqueness. Retain terminal records immutable; derive remote attempt summaries rather than duplicating mutable `supplier_requests` scalar history. Never conflate provider attempts with `jobs.attempts`, which counts local scheduler retries. Record one request with order/quantity and separate same-order, per-unit encrypted fulfillment outputs. Unknown outcomes and unfulfilled partial quantity await safe reconciliation/admin review; no automatic re-purchase.

- **27. `product_supplier_sources` — KEEP (owner-approved 2026-10-29).** Genuine one-product-to-many-provider-product/variant mapping, with product FK, controlled provider code, separate external product/optional variant, enabled/revision/timestamps and null-aware duplicate guards. One provider account/configuration is shared across mappings/brands; no credential copies. Retain one checked product-level active selection and immutable source-revision/account snapshots on paid requests. Final constraint/config design is still reviewed, with no implementation authorized.

## High-value minimum compaction proposal

Without adding tables beyond the **four owner-approved relations**, the most defensible further column reductions are:

1. `orders.public_ref` — use the real global `orders.id` publicly; keep `orders.created_at`.
2. `discount_uses.user_id` and `discount_uses.saved_currency` — derive from `orders`.
3. `support_messages.sender_telegram_id` — derive from ticket's `user_id`.
4. `campaigns.audience_language` — collapse into `language` if both currently mean the same thing.
5. `telegram_deliveries.action` — derive from whether `target_message_id` exists (only while supported operations are send/edit).
6. `brands.require_channel_join` — derive from active required `brand_channels` if no separate bypass switch exists.
7. **Already approved and applied in the candidate**: `wallets.currency` and `wallet_entries.currency` are gone; the USD wallet PK is just `user_id`. `telegram_deliveries.chat_id` is also gone under private-DM-only scope.

**Keep with caution**: `telegram_deliveries.campaign_batch_id` for a cross-language deduplication unique constraint, historic order product/brand snapshots, order FX and calculation version, `payments.amount_due/received`, `discounts.redeemed_count`, `wallet_entries` immutable proof, and `audit_events.brand_id`. These may look repeated but fulfill real constraints.

**Additional integrity finding**: The proposed `campaigns` uniqueness is `(batch_id,brand_id,language)`, so `(batch_id,brand_id)` alone is **not unique** when a brand has multiple language versions. Consequently, a normal FK from `telegram_deliveries(campaign_batch_id,brand_id)` to `campaigns(batch_id,brand_id)` is invalid/inadequate. Keep both `campaign_id` and `campaign_batch_id` only with a checked composite reference to a unique `campaigns(id,batch_id,brand_id)` key (or an equivalent guarded constraint), plus `UNIQUE(campaign_batch_id,user_id)` on materialized recipients. This protects against mismatching the batch ID with the localized campaign used for sending.

## Two alternative integrity designs for customer-owned rows

| Choice | Shape | Database enforcement | Tradeoff |
|---|---|---|---|
| **Lean member FK (current proposal)** | `orders(user_id,product_id,...)`, `telegram_deliveries(user_id,...)` | Triggers ensure selected listing, coupon, campaign, order and user all belong to the same `users.brand_id` | Fewer columns; more trigger logic and joined queries |
| **Composite tenant FK** | `orders(brand_id,user_id,product_id,...)`, `telegram_deliveries(brand_id,user_id,...)` | Composite FKs `(brand_id,user_id)` and `(brand_id,product_id)` enforce tenant integrity directly | One repeated column in hot tables, clearer SQL constraints and indexes |

For a financially sensitive three-brand platform, the second approach is **easier to prove correct**. It is not mandatory; if the owner prefers the first, database-level triggers and explicit cross-brand negative tests are a hard implementation requirement. Removing every `brand_id` column merely to save a few bytes would be a regression.
