# Data Model: Complete EF/plain-content target
**Baseline**: `c44dc1b`; [schema index](../../ops/migrations/SCHEMA_INDEX.md). All 28 entities belong to US1; representation changes also belong to US2. The baseline remains immutable. EF migration history tables are infrastructure outside this business count.
## Common mapping and validation rules
- C# entity types live in `src/Platform.Persistence/Entities/<Entity>.cs`; per-type mappings live in `Configurations/<Entity>Configuration.cs`. Provider-specific overrides share the same logical relationships. Existing DTOs are projections, not replacement persistence entities.
- Each field below names the source physical field/type. Final fields use the explicit rename/removal matrix below; all other fields remain semantically unchanged. Exact nullability, defaults, length/range/enumeration checks, PKs, alternate keys, filtered indexes, foreign keys and delete rules are incorporated from the immutable source links, not re-invented from naming.
- SQLite `TEXT` money validated by `akanti_decimal` maps to decimal with the existing ExactDecimal canonical-text type mapping; no double conversion. PostgreSQL numeric precision/scale comes from its corresponding source declaration. Checked integer amounts/quantity/version remain exact. Validate decimal translation against both provider fixtures; use mapped exact functions where needed, not client-side unbounded filtering.
- UUID fields use Guid with canonical SQLite D text and PostgreSQL uuid; UTC times use existing canonical UTC text/timestamptz. Validate UUID ordering at cursor boundaries for each provider. INTEGER booleans retain 0/1 checks. BLOB content stays byte[] with exact binary equality; text interpretation requires the existing validated codec.
- Explicit composite references retain brand/customer relationships. Use Restrict/NoAction and the current deferrability/guard semantics; never introduce cascade deletion for historical money, orders, audit, evidence or referenced records. Revision/version fields are application-managed concurrency tokens, with expected revision and affected-row checks in each state transition.
- Retain hashes/fingerprints, admin password_verifier/token_hash and payments.ipn_key_id/signature/payload hashes. They support authentication, verification and replay, not content encryption. Do not remove a field solely because its name contains key.

## Financial and workflow state transitions
- Wallet: append one immutable posting and advance wallet version/balance in the same transaction; preserve opening-once, posting sequence, reference identity and compensation provenance. Failed/cancelled changes roll back together.
- Orders: preserve current payment/fulfillment enums and transition predicates. Payment confirmation alone never authorizes release; all allocated units, redeemed discount and complete manifest must satisfy existing release checks. Preserve whole-order preorder allocation and FIFO.
- Payments: awaiting/confirming/review/settled and current expiry/late-payment branches retain exact method, due/received amounts, evidence/signature binding and one compensation. Keep unknown provider effects for review.
- Supplier requests/attempts: retain current submit/status/export parent linkage, attempt sequence, cost ceiling and audited approval. Unknown/timeout does not automatically resubmit a purchase; acquired bonus stock stays quarantined.
- Jobs/Telegram: transactional enqueue, unique dedupe, guarded lease claim, lease-owner completion, durable known success and uncertain-new-send fences; keep original message edit target and manifest generation.
- Discounts: revision plus audit identity remain immutable; hold → redeemed/released follows original order state. Prepaid source entitlement is unique and does not create goods fulfillment.
- Support/campaign/subscription/history: retain authorization, original state enums, intentional retention limits, recipient eligibility, opt-out and one active subscription/notification semantics. Do not invent new transition vocabulary.
