# Plain-target conversion and recovery contract
**Applies to**: US2, FR-006–FR-010; SC-002/SC-004/SC-006. Applies to an existing Akanti target, not a new AccAbad mapping/import feature.
## Formats and storage
The encrypted baseline and new plaintext model have explicit distinct format versions. Fresh targets are created from the final EF migration lineage by an operator command. Existing targets are copied and transformed by an offline SchemaRunner command using isolated old readers; EF writes the destination. All former ciphertext becomes direct original bytes, not ciphertext bytes renamed as content. All encryption-only key identifiers are absent from the final model. Signature metadata/hashes/API/provider credentials and their restricted access remain.
## Command inputs and outputs
Implement explicit subcommands under `src/Platform.SchemaRunner/Program.cs` for inspection, fresh creation/adoption, conversion/resume and final verification. Inputs bind provider, exact source snapshot identity/hash, source schema/format, explicit target path/database, target model/migration identity, private asset roots, private checkpoint/manifest paths and a recovery-only old-key reference. Never accept keys or secret values on argv, URLs or logs. Nonexistent target/empty destination and private ownership/permissions are required. No production defaults or implicit discovery. Existing CLI verbs must remain documented or explicitly retired; final exact option syntax is documented with implementation.
Successful output is a redacted receipt with source/target identity commitments, schema/model/format versions, row/asset totals and digests, validation status and candidate revision. Detailed records/checkpoints remain private and owner-host scoped. A success receipt is not permission to activate that target.
## Ordered conversion protocol
1. Refuse active source writers, unverified provider/schema identity, shared/overlapping paths, symlinks/hard links and incompatible runtime ownership. For synthetic qualification use disposable test copies; any protected execution requires separate authorization.
2. Capture and verify an immutable consistent source snapshot, including committed WAL content and every referenced operational asset. Record identifiers and hashes; keep original database, files, images and old keys intact. Use bounded read-only source access.
3. Create a private fresh final EF target plus separate asset root, preserving original IDs and relations in dependency-safe stages. Resolve cycles with supported deferred constraints or staged optional links inside validated transactions; never disable validation and silently publish. EF migration bookkeeping is excluded from 28-table business row comparisons.
4. Copy all rows and all referenced operational files, decrypting only in the recovery tool with exact old field/context binding. Preserve original bytes, evidence signatures/digests, source fingerprints, amounts/denominations, liability/review states, IDs, audit ordering, dedupe keys, leases and delivery markers. Do not rewrite financial history or mark imported jobs delivered. Any file-format wrapper/digest changes get explicit old/new representation hashes while preserving original verified payload hashes.
5. Persist idempotent bounded checkpoints bound to snapshot, schema/model, key identity and asset manifest. Reusing a checkpoint for another source/key/model is rejected. Partial destinations cannot be opened by daemons. Resume reconciles already-copied fields/assets, not merely row counts; wrong/missing keys and corrupt data preserve the source and block publication.
6. Verify full row/field and asset coverage, original vs new plaintext byte hashes in private evidence, exact balances/postings/liabilities, foreign keys, uniqueness, state/tenant guards and all named pre-commit invariants. Equal counts alone are insufficient. Re-read source snapshot commitments at completion.
7. Emit a verified manifest/receipt. Publish only through a separately authorized explicit operator action with source writers stopped and daemon schema/format guard checks. Never automatically replace an active service target as a side effect of conversion.
## Failure and rollback
- Any interrupted conversion leaves the immutable source and durable private checkpoints available. Destination is unpublishable until full verification; cleanup cannot delete the original or old keys.
- Missing key, malformed envelope, inconsistent asset digest, source drift, schema drift or failed coverage causes a bounded redacted failure. Never infer plaintext from a decryption failure.
- Once new state accepts writes, no automatic encrypted executable/old PostgreSQL writer/stale snapshot fallback is permitted. Roll back only to a qualified executable compatible with the same plaintext schema and accepted DB/WAL/assets; otherwise stop safely for recovery. Do not promise reverse-encryption conversion in this feature.
- No source key retirement, historical archive rewrite, production mutation or live external-effect replay is authorized.
## Required synthetic acceptance
Fresh no-key startup of API/BotHost/JobHost; exact binary/Unicode/null boundary roundtrip; encrypted target with all 28 tables and referenced assets; known old-key, previous-key and wrong-key cases; complete row/field/digest/amount comparison; interruption after committed copy batch and asset batch; mismatched resume identity; duplicate resume; WAL-consistent source snapshot; incompatible-old-executable refusal; same-accepted-state compatible restart and safe-stop recovery. All provider interaction is fake/local and no customer messages are sent.
