# Research: Full EF and encryption removal
**Inspected baseline**: main `48eeccda54275cfaf3c7b5c1ba22eff1d08d650b`; source code is unchanged from `c44dc1b`. Research was performed by one agent; no delegation or live service calls.
## R1 — Complete model, retained providers
**Decision**: Reuse `Platform.Persistence`, add `Entities/`, `Configurations/`, shared `AkantiDbContext` and narrowly derived SQLite/PostgreSQL contexts with separate migration folders/snapshots. Keep both maintained target providers: SQLite staging and PostgreSQL production capability. Neither is activated by this design.
**Rationale**: `AdminProductQuery.cs` maps only seven product fields; `SqliteSession.cs` uses EF for that one query while most stores still issue commands. Constitution IV retains PostgreSQL production. All 28 tables and all retained target paths must convert.
**Alternatives considered**: One-query EF completion, two independently maintained domain models, retiring PostgreSQL implicitly, or adding a generic repository framework; rejected as incomplete, duplicative or outside scope.
## R2 — Dependencies and tooling
**Decision**: Keep .NET SDK 10.0.403/C#14 and current central pins: EF relational/SQLite 10.0.15, Npgsql provider 10.0.3. Add matching EF Design and local dotnet-ef tooling only during implementation, with private design dependencies and reviewed lock-file updates. Prove current provider compatibility before changing package versions; no speculative package upgrade is part of planning.
**Rationale**: `global.json`, `Directory.Build.props`, `Directory.Packages.props` and the persistence project establish the actual stack. Existing managed publishes remain authoritative; no new full-EF AOT compatibility claim.
**Alternatives considered**: Framework upgrades or a new project per provider; unnecessary to meet the request.
## R3 — Exact data and transactions
**Decision**: Retain original precision, currency labels, IDs, UTC timestamps and binary content. SQLite money stays canonical exact decimal text, never floating point; PostgreSQL keeps existing numeric precision. Use explicit unit-of-work transactions for multi-step business operations, not isolated SaveChanges calls. Keep SQLite WAL/foreign keys, immediate writer/deferred reader transactions and finite timeout. EF joins the existing provider transaction while paths convert. Final target business reads/writes use LINQ/tracked changes or guarded EF set-based operations; a unit-of-work performs flushed-state validation before committing.
**Rationale**: `SqliteSession.cs`, `SqliteSchema.cs`, `SqliteIntegrity.cs`, `DbSession.cs` and baseline indexes already enforce these semantics. EF transactions can share an existing connection/transaction. SQLite migration rebuilds can lose artifacts not represented in the model. Translation and ordering are qualification obligations, not assumed equivalence.
**Alternatives considered**: double-valued amounts, per-call automatic transactions, removing integrity checks or automatic external-effect retries; rejected because they change money/recovery semantics.
## R4 — SQL boundary
**Decision**: No target business SQL escape hatch. Permit reviewed connection PRAGMAs, schema/migration DDL including database integrity triggers/functions, and read-only catalog identity inspection. Reimplement pre-commit business assertions with EF queries and exact arithmetic, retaining only independently justified database integrity primitives. Historical baselines and read-only legacy-source tools remain preserved; existing import tools' target writes must convert to EF even though new mapping/import work is excluded.
**Rationale**: EF cannot replace all provider configuration/DDL. Blanket retention of current checkout, payment or job SQL would defeat FR-002/FR-004.
**Alternatives considered**: Banning generated SQL/DDL, preserving every old SQL store as an exception, or excluding target writes merely because their project is named Migration; all rejected.
## R5 — Plain operational content
**Decision**: Remove target encryption services and encryption-only key grants/IPC. Keep former byte content as unencrypted BLOB/byte[] with explicit plaintext names, preserving original byte sequences. Keep signatures, hashes, fingerprints, credential-file permissions, tenant authorization and bot/provider/API credentials. In particular `payments.ipn_key_id` identifies verification material and is NOT an encryption key column to drop. Reference-only evidence files, manifest files and inbox archives must also be inventoried, not inferred from SQL column names.
**Rationale**: `BrandCipher`, `InventoryCipher`, `SecretSnapshot`, `SqliteStageInventoryBridge`, provider adapters and host bootstrap couple target operations to encryption. `StagingPreviewBot.cs` also uses direct inbox encryption. Stored content and required authentication secrets are distinct.
**Alternatives considered**: Identity encrypt/decrypt wrappers, empty dummy key files, leaving ciphertext-named fields active, or removing verification/hashing along with encryption; rejected.
## R6 — Existing targets and recovery
**Decision**: Use an offline copy-and-convert tool with both old readers isolated in migration/recovery tooling and new EF writers. Freeze a verified source copy, bind exact source/target schema identities and snapshot, create a new private target, copy all 28 tables and referenced assets, validate complete content/identity/financial coverage, then publish only with explicit operator action. Checkpoints are bound to source hashes and resume idempotently. Conversion reads original keys only in that tool, never in target daemons. Keep source immutable and retain all historical keys/backups. Once converted data accepts writes, rollback requires a proven plaintext-schema-compatible executable using the same accepted state; restoring a stale encrypted snapshot is forbidden.
**Rationale**: Renaming BLOBs does not decrypt values; changing columns in place or auto-detecting plaintext cannot prove coverage and recovery.
**Alternatives considered**: Destructive ALTER-only conversion, implicit startup migration, production-source modification or stale database rollback; rejected.
## R7 — Governance and scope
**Decision**: Record the owner's existing full-EF and target-encryption-removal decisions in constitution 4.0.0 as a scoped feature-005 override. Preserve historical requirements and every pinned baseline/evidence artifact. Exclude new AccAbad mappings, protected import execution, feature 002 work, live provider activation and deployments. All generated implementation tasks remain unchecked.
**Rationale**: Constitution 3.1.0 requires target keyrings; spec FR-013 calls for the approved prospective amendment before implementation. A major version identifies the removed at-rest safeguard. Plain database/WAL/assets/backups expose content to anyone with storage access; owner-managed host/storage protection, restricted files, authentication and redaction remain required. This is the recorded tradeoff already selected by the owner, not a new approval request.
**Alternatives considered**: Silently ignoring the contradiction or rewriting historical approvals; rejected.
