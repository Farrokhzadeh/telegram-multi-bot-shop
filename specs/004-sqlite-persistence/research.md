# SQLite design decisions

- **Database** — Use one local file with WAL and foreign keys enabled on each connection. WAL permits reads while writes take turns. Keep a finite busy timeout and use immediate write transactions for read-modify-write operations. Retain PostgreSQL for production. See [SQLite WAL](https://sqlite.org/wal.html) and [transactions](https://sqlite.org/lang_transaction.html).
- **Amounts** — Store exact decimal values as invariant text with the existing denomination and accepted precision. Validate and calculate with exact decimals inside the write transaction. Port SQL aggregates, comparisons and ordering explicitly. Binary floating point loses precision, and one fixed scale would constrain fields that use different precision. See [Microsoft.Data.Sqlite types](https://learn.microsoft.com/dotnet/standard/data/sqlite/types).
- **Integrity** — Use SQLite constraints where equivalent. Move PostgreSQL deferred trigger assertions that need several rows to pre-commit checks in the same serialized write transaction. Keep the existing unique replay keys, lease fences and immutable ledger checks. Use the EF SQLite provider for the existing catalog query. See [provider limitations](https://learn.microsoft.com/ef/core/providers/sqlite/limitations).
